# Supabase Backend Foundation — Design

**Status:** Awaiting approval before implementation  
**Scope:** Phase 1.5 only

## Intent

Prepare the existing Hobby & Habit Discovery Expo app for a later Supabase integration. The work will establish a safe, repeatable database and Storage foundation, typed service boundaries, and centralized authentication while keeping the current four screens and local discovery experience intact.

## Repository findings

- Expo SDK 58.0.22, React Native 0.88.1, Expo Router, and TypeScript are already installed.
- `@supabase/supabase-js` 2.118.0 is installed. The current client uses `expo-secure-store`, requires both credentials, and deliberately stays disabled on web.
- The `hobby` deep-link scheme is already present in `app.json`; `expo-linking` is installed.
- The nine-item interest catalogue and category/search state are local. No Supabase migrations, services, generated database types, or backend tests exist yet.
- There is no configured Supabase project, Supabase CLI executable, or Docker executable in the workspace environment. Remote database validation and CLI type generation therefore cannot be assumed.

## Goals

- Keep the app launchable and local discovery usable without Supabase credentials, while returning an explicit configuration error from backend operations.
- Centralize a typed Supabase client and auth, profile, database, and media access outside UI components.
- Add reproducible migrations for all nine requested tables, their constraints and indexes, public catalogue read rules, user ownership rules, and the private `activity-media` bucket.
- Prepare email/password and Google/Apple OAuth service entry points without adding authentication UI.
- Document local setup, dashboard requirements, generation commands, and the distinction between locally prepared and live backend functionality.

## Non-goals and anti-goals

- Do not change or replace Discover, Explore, Media, Profile, search, category filters, themes, or the local catalogue.
- Do not integrate catalogue fetching, attempts, check-ins, journals, notifications, or media into screens.
- Do not add Cloudflare services, another state library, service-role credentials, public photo URLs, invented catalogue records, or a fabricated “connected” result.
- Do not claim migrations or provider configuration are live unless they have actually been applied.

## Approaches considered

1. **Use Supabase’s documented React Native storage pattern (selected).** Store native sessions in AsyncStorage and let Supabase use its browser storage on web. This avoids imposing a SecureStore value-size failure on full sessions and avoids custom token persistence code. The trade-off is that AsyncStorage does not encrypt data at rest.
2. **Keep SecureStore and add chunking/fallback logic.** This preserves encrypted storage but requires a custom token-storage and recovery mechanism. Expo documents that the underlying iOS platform can reject values around 2 KB, and the app would need to own more persistence edge cases. This is not selected.

The user selected the first approach. Supabase’s current React Native guide recommends AsyncStorage for native persistence, and the app will use `expo install` for SDK-compatible dependencies. The existing `hobby` scheme will support the OAuth return URL; provider completion remains dependent on dashboard configuration.

## Design

### Client and services

- The mobile bundle contains only `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; do not support or document a legacy anon-key variable. Never include a service-role key. Validate the URL and report invalid configuration clearly.
- Keep client creation optional. Missing or invalid public configuration yields a typed, explicit configuration error for backend calls, not an apparent success; no screen depends on the client being present, so existing local discovery continues to launch.
- Follow Supabase’s documented React Native client setup: use `@react-native-async-storage/async-storage` on iOS and Android, Supabase’s default browser storage on web, persist sessions, and enable automatic refresh. Set `detectSessionInUrl: false` on native and leave browser URL detection enabled on web. Use a single React Native `AppState` listener to start/stop refresh. Document that AsyncStorage does not provide application-level encryption at rest; no custom SecureStore adapter will be introduced. Remove `expo-secure-store` and its config plugin if repository inspection confirms there are no remaining uses.
- Use the supported React Native URL polyfill required by the Supabase client setup.
- Put email signup/sign-in, sign-out, current/restored session, auth-state observation, and Google/Apple OAuth entry points in `src/lib/supabase/auth.ts`. Native OAuth returns to the exact app URL `hobby://auth/callback`; the service opens the provider URL in the system auth browser and exchanges the returned authorization code for a Supabase session. It must return real Supabase/provider errors when provider setup is missing.
- Anonymous users can continue browsing the local Discover and Explore content. Future personal-data service calls require an authenticated session and are independently protected by RLS; this phase adds no auth gate or sign-in UI to the screens.
- Keep profile reads/updates and media upload/signed-URL/deletion operations in service modules. Deleting media removes the Storage object first and deletes metadata only after Storage confirms success. If metadata insertion after upload fails, attempt object cleanup and report cleanup failures.
- Keep server-derived catalogue records out of Zustand; do not add server cache or UI integration in this phase.

### Database and access rules

- Create `profiles`, `categories`, `interests`, `starter_ideas`, `attempts`, `checkins`, `journal_entries`, `media_assets`, and `notification_preferences` in one timestamped migration.
- The schema contract is the field list in the Phase 1.5 request: `profiles(id, display_name, avatar_path, created_at, updated_at)`; `categories(id, name, slug, description, sort_order, is_published, created_at)`; `interests(id, category_id, name, slug, description, type, cover_image_path, is_published, created_at, updated_at)`; `starter_ideas(id, interest_id, title, description, instructions, estimated_minutes, difficulty, sort_order, is_published, created_at)`; `attempts(id, user_id, interest_id, starter_idea_id, custom_title, intention_note, planned_for_date, status, started_at, completed_at, dropped_at, created_at, updated_at)`; `checkins(id, user_id, attempt_id, local_date, result, created_at)`; `journal_entries(id, user_id, attempt_id, content, created_at, updated_at)`; `media_assets(id, user_id, attempt_id, journal_entry_id, storage_path, mime_type, file_size, created_at)`; and `notification_preferences(id, user_id, morning_enabled, morning_time, evening_enabled, evening_time, timezone, updated_at)`.
- `categories`, `interests`, and `starter_ideas` are shared catalogue records, each with its own `is_published` flag. `interests.type` is limited to `hobby`, `habit`, or `both`. `starter_ideas` are not user-owned. A media asset always belongs to one user-owned attempt and may optionally point to a journal entry on that same attempt.
- Attempts allow only `planned`, `active`, `completed`, and `dropped`; check-ins allow only `tried` and `skipped`, with one record per attempt and `local_date`. A custom attempt with no `interest_id` must have `custom_title`. `interest_id`, `starter_idea_id`, and `custom_title` are nullable as described in the request; lifecycle timestamps are nullable until the corresponding event occurs. Other nullable fields are limited to profile display/avatar, catalogue descriptions/cover paths, starter-idea description/instructions, and optional media journal link. Difficulty remains text because the request does not define a difficulty vocabulary.
- **Builder call:** when an attempt has a `starter_idea_id`, it must also have the matching non-null `interest_id`; custom attempts cannot reference a catalogue starter idea. Enforce this with a composite foreign key to `(starter_idea_id, interest_id)` on `starter_ideas`.
- Add `CHECK (starter_idea_id IS NULL OR interest_id IS NOT NULL)` alongside the composite foreign key, so PostgreSQL null handling cannot bypass the starter-idea/interest match. Also retain the custom-title check: `interest_id IS NOT NULL OR custom_title IS NOT NULL`.
- Enforce these attempt transitions in the database: `planned → active`, `planned → dropped`, `active → completed`, and `active → dropped`. `completed` and `dropped` are terminal. Only `record_checkin` may transition `planned → active`; a separate `transition_attempt` RPC handles `planned → dropped` and `active → completed/dropped`. No direct client UPDATE privilege is granted on `status`. A trigger rejects other status changes and any change to lifecycle timestamps outside a valid transition; it sets the corresponding timestamp itself on a valid transition.
- Every new attempt starts as `planned`; its insert trigger rejects any other initial status and leaves lifecycle timestamps null. `id`, `user_id`, and `created_at` are immutable after insert. The database supplies their defaults (`gen_random_uuid()`, `auth.uid()`, and `now()` respectively); column-level INSERT grants do not let clients override them. `updated_at` is set by a database trigger on every update. Clients cannot directly update `started_at`, `completed_at`, `dropped_at`, `updated_at`, or the immutable fields.
- Check-ins are append-only historical records. Owners can read check-ins for their own attempts; the client receives no direct INSERT, UPDATE, or DELETE privilege or policy on the table. All inserts go through the atomic `public.record_checkin` RPC. A mistaken entry is not silently overwritten or erased in this phase. Check-ins on completed or dropped attempts remain readable as history but cannot be added. They are removed only as part of an explicit parent-attempt or account deletion; those destructive flows must clearly confirm the associated history removal.
- `record_checkin(p_attempt_id, p_local_date, p_result, p_local_timezone)` is a narrowly scoped `SECURITY DEFINER` PL/pgSQL function with an empty/fixed `search_path`, explicit `auth.uid()` ownership validation, and `EXECUTE` granted only to `authenticated`. It locks the owned attempt row, accepts only `planned` or `active`, validates the IANA timezone, and rejects dates before `planned_for_date` or after the current local date computed in that timezone. On a `planned` attempt it first changes status to `active`; the status trigger sets `started_at`. It then inserts the check-in, whether `tried` or `skipped`, and returns the inserted row. The transition and insert occur in one database transaction: any validation, uniqueness, or insert error rolls back both writes. The function cannot be called for another user's attempt. RLS remains enabled; because the function is definer-owned, these explicit checks are mandatory, and direct table inserts stay revoked.
- `transition_attempt(p_attempt_id, p_new_status)` is another narrowly scoped owner-checking RPC. It locks the user's attempt and accepts only `planned → dropped`, `active → completed`, or `active → dropped`; `planned → active` is reserved for the first check-in operation. The lifecycle trigger sets the corresponding timestamp and `updated_at`.
- Clients may update their own `intention_note` directly through a column-level UPDATE grant and the normal owner RLS policy. They cannot directly update `planned_for_date`; it is changed only by `set_attempt_planned_date(p_attempt_id, p_new_date, p_local_timezone, p_acknowledge_skipped_pair)`, an owner-checking RPC. It accepts only `planned` or `active` attempts, validates a valid IANA timezone, and rejects a past local date. On an active attempt with skipped history, the new planned date must be after the latest skipped local date. If an unacknowledged two-day prompt is pending, the caller must explicitly pass `p_acknowledge_skipped_pair = true`; the function then requires the new date to be after that pair. Passing `true` without a pending pair is rejected. Thus ordinary note edits and direct column updates cannot acknowledge or bypass the prompt. Advancing `planned_for_date` beyond the pair is the persisted acknowledgement, so no extra acknowledgement table/column is needed. The function updates `updated_at` through the database trigger.
- **Retry semantics:** after a skipped day, retrying an existing `active` experiment updates that same attempt's `planned_for_date` through `set_attempt_planned_date` and leaves every existing check-in intact. Choosing “Try again” from the two-day decision prompt explicitly acknowledges it through the RPC and sets `planned_for_date` after the latest skipped local date. It does not create another attempt. If the user explicitly completed or dropped the experiment and later wants to try the interest again, create a new `planned` attempt; do not reopen the terminal row. Do not add a uniqueness rule on `(user_id, interest_id)`. Completing, dropping, or retrying never deletes prior check-ins, journal entries, or media references.
- **Two-day decision rule:** a future application service will show a decision prompt when an active attempt has explicit `skipped` check-ins for two adjacent values of `local_date` (`d` and `d - 1`) and the later skipped date has reached or passed the attempt's current `planned_for_date`. `local_date` is the user's local calendar date supplied by the app and stored as PostgreSQL `date`. A missing row is absence of data and is never treated as `skipped`; skipped check-ins do not alter the overall attempt status. When the user chooses “Try again,” advancing `planned_for_date` beyond that skipped pair acknowledges it, so the same pair cannot trigger the prompt repeatedly. The database enforces one check-in per attempt per local date. This phase defines the rule and schema, but does not add the prompt UI or full attempt lifecycle screens.
- The relationship chain is `auth.users → profiles`; `categories → interests → starter_ideas`; `auth.users → attempts → checkins/journal_entries/media_assets`; and optional `journal_entries → media_assets`. `attempts.interest_id` may be null for custom activities. `notification_preferences` has at most one row per user.
- **Builder call:** notification preference rows are created only when the user first saves notification settings, not during sign-up. Both reminders default disabled; `morning_time` defaults to `08:00`, `evening_time` to `20:00`, and `timezone` to `UTC` as a safe fallback. The preference service writes the user's IANA timezone when settings are saved. These defaults do not schedule notifications in this phase.
- Use UUIDs, appropriate text/date/time/time-zone/timestamp types, foreign keys, checks, unique constraints, `updated_at` triggers where needed, and indexes for ownership and common category/attempt lookups.
- Use composite ownership relationships so a check-in, journal entry, media row, or starter idea cannot be attached across users or to a mismatched interest/attempt. Add the parent-side unique keys required by PostgreSQL for each composite FK: `starter_ideas UNIQUE (id, interest_id)` for `attempts (starter_idea_id, interest_id)`; `attempts UNIQUE (id, user_id)` for `checkins`, `journal_entries`, and `media_assets (attempt_id, user_id)`; and `journal_entries UNIQUE (id, attempt_id, user_id)` for `media_assets (journal_entry_id, attempt_id, user_id)`. The referenced columns on each FK must match the unique key in both column identity and order. Keep primary keys on each `id`; these additional unique constraints exist specifically to validate the composite relationships.
- **Builder call:** auth-user deletion may cascade profiles, attempts, check-ins, journal entries, and notification preferences, but it must be restricted while any media metadata remains. The future account-deletion operation must remove each owned Storage object first, remove its metadata row only after successful object removal, and then delete the Auth user. Attempt deletion cascades check-ins and journal entries but is restricted while media metadata exists; callers must perform the same Storage-first cleanup for the attempt before deleting it. Deleting a journal entry clears only the optional media-to-journal link. Dropping or completing an attempt does not delete any history. Deleting categories, interests, or starter ideas with dependants is restricted; catalogue rows should normally be unpublished instead of hard-deleted. This avoids losing personal references or orphaning private objects. Account deletion and attempt lifecycle UI are outside this phase, so document the required future cleanup order rather than adding a service-role or SQL-based Storage deletion path.
- Create profiles from `auth.users` with a fixed-search-path security-definer trigger. Use a least-privilege profile policy: a user may read/update their own profile; the trigger owns insertion and deletion.
- Enable RLS on every app table. Public roles can select published categories, interests, and starter ideas; catalogue writes are revoked from mobile roles. Interests are visible only when both the interest and its category are published. Starter ideas are visible only when the idea, its interest, and the interest's category are all published. An unpublished parent therefore never exposes associated child records.
- Protect profiles, attempts, check-ins, journal entries, media metadata, and notification preferences with RLS. Use both `USING` and `WITH CHECK` where applicable. Composite foreign keys and owner predicates prevent attaching a row to another user's attempt; frontend checks are not a security boundary.
- Attempt RLS permits inserts only for `user_id = auth.uid()` with initial `planned` status and null lifecycle timestamps; updates and deletes require the existing row to belong to `auth.uid()`, with `WITH CHECK` preserving ownership. Column grants then limit direct attempt updates to `intention_note`; lifecycle and scheduled-date RPCs independently verify `auth.uid()` and the row owner before changing protected fields.
- Define PostgreSQL grants explicitly in the migration after revoking existing/default app-table grants. Grant `USAGE` on `public` to `anon` and `authenticated`. Grant `SELECT` on the three catalogue tables to both roles, with no catalogue write grants. Grant `SELECT` and column-level `UPDATE (display_name, avatar_path)` on `profiles` to `authenticated` (profile insertion/deletion is trigger-owned). Grant `SELECT, DELETE` on `attempts`, column-level `INSERT (interest_id, starter_idea_id, custom_title, intention_note, planned_for_date)`, and column-level `UPDATE (intention_note)` to `authenticated`; all other attempt creation/updates use database defaults or the lifecycle/date RPCs. Grant `SELECT, INSERT, UPDATE, DELETE` on `journal_entries` and `notification_preferences` to `authenticated`; grant `SELECT, INSERT, DELETE` on `media_assets`; and grant only `SELECT` on `checkins` (inserts require the RPC). Grant no personal-table privileges to `anon`. Grant `EXECUTE` on `record_checkin`, `transition_attempt`, and `set_attempt_planned_date` only to `authenticated`, revoking default execution from `PUBLIC` and `anon`. RLS remains enabled: personal-row policies scope access to `auth.uid()`, while catalogue policies require the appropriate publication flags and published parents. For `storage.objects`, grant only `SELECT, INSERT, DELETE` to `authenticated`, none to `anon`, and no update/upsert privilege; Storage RLS verifies ownership and attempt association.
- The migration's privilege statements will follow this minimum pattern (the migration runs as `postgres`):

  ```sql
  ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
    REVOKE ALL ON TABLES FROM anon, authenticated;
  REVOKE ALL PRIVILEGES ON TABLE public.categories, public.interests,
    public.starter_ideas, public.profiles, public.attempts, public.checkins,
    public.journal_entries, public.media_assets, public.notification_preferences
    FROM anon, authenticated;
  GRANT USAGE ON SCHEMA public TO anon, authenticated;
  GRANT SELECT ON TABLE public.categories, public.interests, public.starter_ideas
    TO anon, authenticated;
  GRANT SELECT ON TABLE public.profiles TO authenticated;
  GRANT UPDATE (display_name, avatar_path) ON TABLE public.profiles TO authenticated;
  GRANT SELECT, DELETE ON TABLE public.attempts TO authenticated;
  GRANT INSERT (interest_id, starter_idea_id, custom_title, intention_note,
    planned_for_date) ON TABLE public.attempts TO authenticated;
  GRANT UPDATE (intention_note) ON TABLE public.attempts TO authenticated;
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE public.journal_entries,
    public.notification_preferences TO authenticated;
  GRANT SELECT ON TABLE public.checkins TO authenticated;
  GRANT SELECT, INSERT, DELETE ON TABLE public.media_assets TO authenticated;
  GRANT USAGE ON SCHEMA storage TO authenticated;
  REVOKE ALL PRIVILEGES ON TABLE storage.objects FROM anon, authenticated;
  GRANT SELECT, INSERT, DELETE ON TABLE storage.objects TO authenticated;
  REVOKE ALL PRIVILEGES ON FUNCTION public.record_checkin(uuid, date, text, text)
    FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION public.record_checkin(uuid, date, text, text)
    TO authenticated;
  REVOKE ALL PRIVILEGES ON FUNCTION public.transition_attempt(uuid, text)
    FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION public.transition_attempt(uuid, text)
    TO authenticated;
  REVOKE ALL PRIVILEGES ON FUNCTION public.set_attempt_planned_date(uuid, date, text, boolean)
    FROM PUBLIC, anon, authenticated;
  GRANT EXECUTE ON FUNCTION public.set_attempt_planned_date(uuid, date, text, boolean)
    TO authenticated;
  ```
- Profile fields are limited to the requested display name and avatar path; auth email and provider identities remain in Supabase Auth and are not copied into `profiles`.
- Insert the private `activity-media` bucket in the migration with a 10 MiB object limit and JPEG, PNG, and WebP MIME allowlist. Storage policies enforce the `<user UUID>/<attempt UUID>/<file UUID>.<extension>` shape, `auth.uid()` ownership, and an owned attempt for insert, select, and delete. Uploads will not use upsert.
- Store only paths and metadata in PostgreSQL. Generate short-lived signed URLs for display; never persist them. HEIC conversion remains outside this phase.
- Upload flow: validate supported MIME type and size, upload the object, then insert metadata. If upload fails, create no metadata; if metadata insertion fails, attempt to remove the uploaded object and report any cleanup failure. Delete flow: verify ownership, remove the Storage object, and only then delete metadata. If object removal fails for a reason other than “already absent,” preserve metadata. Make deletion idempotent: if Storage reports the object is already absent, verify absence through an owner-scoped Storage lookup before deleting its metadata. If object removal succeeds but metadata deletion fails, retain the row and return an explicit partial-failure result; a retry verifies the object is absent and safely removes the remaining metadata. Never report complete success until both steps are complete. Attempt deletion is restricted while media metadata exists, so Storage cleanup must happen first.

### Catalogue seed and database types

- Preserve `src/data/interest-catalog.ts` unchanged. `seed.sql` will contain no catalogue rows because the existing records do not provide reliable hobby/habit type classification. The catalogue migration phase can add mapped rows later.
- Apply the migration to a local Supabase database, then generate `src/types/database.types.ts` from that actual schema with the Supabase CLI (`supabase gen types typescript --local --schema public`). Do not hand-author a substitute while claiming it was generated. If the required local stack cannot run and no connected project is available, report type generation as blocked and request access to a real schema before claiming this completion criterion.

### Expo and OAuth configuration

- Add only SDK-compatible dependencies required for persistent sessions, URL handling, and system-browser OAuth callbacks (`@react-native-async-storage/async-storage`, the Supabase-required React Native URL polyfill, and `expo-web-browser` as needed by the callback flow).
- Retain the existing `hobby` scheme. Add `hobby://auth/callback` to Supabase Auth's allowed redirect URLs. In the Google and Apple provider dashboards, configure the Supabase project's provider callback URL shown by Supabase (normally `https://<project-ref>.supabase.co/auth/v1/callback`); this provider callback is distinct from the app callback. Provider secrets and enablement stay in Supabase/Google/Apple dashboards; none go in the mobile bundle.
- Do not add auth routes or change the app’s navigation in this phase.

### Setup and validation

- Create `supabase/config.toml`, a timestamped migration, and `supabase/seed.sql`; update `.env.example` and README setup instructions.
- Use a reproducible CLI workflow: `supabase start` / `supabase db reset` for a clean local build, `supabase gen types typescript --local --schema public` for types, and `supabase link` plus `supabase db push` only when a user-configured project is available. Do not claim the remote project was changed unless a remote push actually completes.
- Add focused unit coverage for missing configuration, client initialization, session restoration/auth handling, centralized error behavior, and media path construction. Add SQL/pgTAP tests and local Storage API checks for the migration, lifecycle constraints, RLS, and private bucket.
- Database lifecycle tests verify new attempts start planned, only documented transitions are accepted, transition timestamps are set, terminal attempts cannot be reopened, and the composite FKs resolve to the exact declared unique keys. Invoke `record_checkin` for a planned attempt on its planned local date with both `tried` and `skipped`: in both cases assert status becomes active, `started_at` is set, and one check-in is inserted. Verify the same transaction rejects dates before the planned date, future local dates, invalid timezones, duplicate attempt/date values, and another user's attempt; on every failure the attempt remains planned with no partial check-in. Verify direct INSERT/UPDATE/DELETE on checkins is denied. Verify direct UPDATE of attempt ids, ownership, created/lifecycle timestamps, status, `updated_at`, and `planned_for_date` is denied; direct updates to `intention_note` succeed and fire the `updated_at` trigger. Exercise `transition_attempt` only for allowed edges. Exercise `set_attempt_planned_date` for an ordinary reschedule, an active retry, a pending skipped-day prompt without explicit acknowledgement (must fail), and an acknowledged retry set after the pair (must succeed); retries update the same row, while completed/dropped retries create a new row without altering prior history. Test the two-day decision predicate against adjacent local dates, a missing date, non-adjacent skips, different attempts, and acknowledgement after `planned_for_date` advances. Verify notification rows default disabled with the stated times/timezone.
- RLS and privilege test strategy: create two distinct local Auth test users. Verify the migration grants only the listed table operations; each user can read and mutate only the operations permitted for their own records, while user A cannot select, update, or delete user B's rows or attach a journal entry or media record to B's attempt, nor call `record_checkin` for B's attempt. Verify neither user can directly insert, update, or delete check-ins. Also verify anonymous users read only published catalogue records, unpublished interests/categories hide associated starter ideas, and no catalogue writes are granted. Test Storage upload/read/delete for the owning user and reject the other user, an unpublished/unknown attempt, invalid MIME type, oversized file, and malformed path. Delete a Storage object first, then retry media deletion with metadata remaining and verify the owner can clean up that metadata idempotently.
- Validate migration reproducibility by resetting an empty local Supabase database and checking all schema, bucket, and policies are created from versioned files. If Docker/CLI or a connected test project is unavailable, clearly report migration, type generation, RLS, and Storage checks as unverified rather than substituting fabricated results.
- Run and report TypeScript, ESLint, existing regression tests, Expo Doctor, Expo dependency validation, and Android JavaScript bundle export. Also verify configured native session restoration across an app restart when a test Supabase project is available; local unit tests alone do not prove remote Auth integration.
- Keep `.env` ignored and `.env.example` limited to the project URL and publishable key. Dashboard tasks include email Auth setup, Google/Apple provider credentials and redirect allowlist, and remote migration application; distinguish each from locally prepared code.

## Implementation calls left to the builder

- Use a single timestamped initial schema migration with clear comments and idempotent bucket setup.
- Use explicit per-table policies and shared SQL helper functions only when they reduce repetition without introducing RLS recursion.
- Select practical indexes from foreign-key and common user-scoped access patterns; avoid speculative indexes.
- Report all unavailable remote checks and any CLI-generated artifact that could not be produced without project access.
